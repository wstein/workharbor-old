# Next alpha release plan

Planning snapshot: 11 October 2026. **Not a release-readiness statement.**
`v0.1.0-alpha.6` is a tentative name, not a reserved tag. The previous
published release is [v0.1.0-alpha.5](v0.1.0-alpha.5.md), published 9 October.
Tracking issue: #544. Recheck the published release list before selecting a tag.
This plan and the
[QA plan](v0.1.0-alpha.6-qa.md) are planning records, not the release summary
that the release workflow consumes.

## Purpose and scope

The next alpha should let a human start and supervise long interactive runs in
an existing Docker-compatible runtime, with persistent vendor logins, a stock
language image and the read-only BundleDock toolbox. It must preserve human
initiation and human merge, and make unsupported capabilities visible.
The requirement baseline is [catalog version 3](../content/docs/requirements.md).

The proposed scope is #533–#538. #542, #27, #230, #283 and #35 are dependencies
or evidence gates, not implied completed features. A human settles any scope
reduction or change in order. Source merges alone do not satisfy target-host
acceptance. Deferred requirements R-33 and R-34 remain explicit later work;
this alpha must neither promise a credential proxy nor an egress allowlist.
Native Codex (#35) and skill-neutral integration (#283) are conditional support
claims: they need acceptance if included, but this plan does not require both
to ship in this alpha. Record a human-approved deferral and remove the claim
when either is excluded. The quota/security disposition, tool-event/tool-only
abort acceptance and forge enforcement proof are release gates for the proposed
core scope, not optional documentation caveats.

## Entry gates and integration order

1. Record the scope and dependency disposition for every issue above. The
    human has authorized the direction of optional real Docker quota support,
    contingent on the retained #536 design coverage interpretation, still pending.
    Resolve hard disk quota/security admission through that design and human
    process; optional support grants no implicit unbounded exception. The
    maintainer reports that the system uses Btrfs, but the daemon storage driver,
    qgroups and actual writable mounts/enforcement remain unverified. This
    devcontainer has no Docker CLI/socket; its virtiofs workspace does not
    contradict a Btrfs filesystem in the host VM. Measure coverage of workspace,
    agent home and temporary/private exec storage before claiming full
    `DiskQuota`; rootfs storage options alone are insufficient. This direction
    authorizes no build, live test or host change.
2. Finish runtime/setup integration and tool-store/shim compatibility work;
    then finish duration removal, correlated tool events, tool-only cancellation,
    notifications and remote control. Documentation must describe the resulting
    behavior, including limits, rather than a proposed implementation.
3. Select one exact integrated commit. Record its full SHA, parent/base,
    constituent commits, applicable runtime capabilities and configuration.
    Each required independent reviewer must review that same SHA. Record the
    repository-required review quorum and each `CLEAR <full sha>` result;
    a component review cannot stand in for the integrated review. A changed SHA
    requires fresh applicable checks and reviews.
4. Pass source checks and satisfy the [QA entry gate](v0.1.0-alpha.6-qa.md#entry-gate).
    Author and reviewer must distinguish source/fake results from target evidence.
    Do not begin a target action outside its human-authorized scope.

## Approval and release sequence

This plan authorizes no build, tag, publication, installation, runtime creation,
schedule or host change. Routine source tests, formatting and compiler checks
may run. Artifact, image, CLI and documentation builds each require explicit
human approval, including delegated targets. Installation and consumer image
activation need separate approval. Only the human merges, tags and publishes.
No automation may start, resume or retry product runs; an alert or Decision
waits for a human action.

After the human merges the reviewed changes, freeze the integrated candidate
and complete the QA evidence gates. Write the actual `docs/releases/<tag>.md`
from [TEMPLATE.md](TEMPLATE.md), preserving its install block and truthful known
limits. The [release manual](../content/docs/manual/install-upgrade-release.md#cut-a-release-the-maintainer)
remains the authority for signed tags, green main CI, drafts and provenance.
A human must approve the concrete build and tag candidate before any release
workflow is triggered. A failed immutable tag requires a new tag.

Once a human has authorized a draft build, inspect the archive, checksums, SBOM
and attestation against the exact tagged SHA. A separately authorized test-host
installation must pass upgrade, rollback and smoke acceptance. Present that
evidence, draft notes and outstanding limits for human publication approval.
A prerelease must not activate the Homebrew tap. Documentation publication and
consumer activation are separate approved actions.

## Exit gate and stop conditions

The release record must contain the exact candidate and tag SHA, green checks,
review quorum, target matrix, evidence links for every QA row, approval records,
archive digests/provenance, and the upgrade/rollback result. Any failed mandatory
row blocks release. An unmeasured optional capability remains unverified in the
notes and support matrix, with a named follow-up and human scope decision.

Stop on automatic starts/resumes/retries, run-wide timeout or cancellation used
as a substitute for a tool abort, secret disclosure, forbidden mounts, forge
merge/tag/release/deploy permission, mismatched provenance, or an unresolved
quota/security requirement. Do not relax a control to make the alpha pass.
A documentation-only or fake-backed pass cannot close a live acceptance gate.
